Signing and Audit¶

Signers (HSM / KMS)¶

signing.py

Pluggable CA signing: the CA private key does not have to live in this process.

  • CASigner — the protocol every signer implements: expose the CA public key and sign raw bytes.

  • KeySigner — a signer backed by an in-memory private key (the classic file-based CA).

  • Pkcs11Signer — a signer backed by a key inside a hardware security module or smart card, reached through a PKCS#11 module (tiny-ca[hsm]).

  • sign_builder() — signs any cryptography certificate or CRL builder with a CASigner.

cryptography can only sign with its own key objects. For external signers sign_builder() therefore builds the to-be-signed structure with a throw-away key of the same algorithm, has the external signer sign those exact bytes, splices the real signature into the DER encoding and verifies the result against the CA public key before returning it.

class tiny_ca.signing.Pkcs11Signer(key, public_key, mechanisms=None, session=None)[source]

Bases: object

A CASigner whose private key never leaves a PKCS#11 token (HSM, smart card, SoftHSM, cloud HSM with a PKCS#11 module).

Use open() to log in to a token, or wrap an already opened python-pkcs11 private key object. The CA public key is taken from the CA certificate, so the token only needs to hold the private key. Signing is serialised with a lock because PKCS#11 sessions are not thread-safe.

Parameters:

  • key (Any) – A python-pkcs11 private key object (anything with sign(data, mechanism=...)).

  • public_key (PublicKey) – The CA public key (ca_cert.public_key()).

  • mechanisms (Any) – Namespace holding the PKCS#11 mechanism constants; defaults to pkcs11.Mechanism.

  • session (Any) – Session to close in close() (set by open()).

Audit log¶

audit.py

Tamper-evident audit log for CA operations.

Every security-relevant operation (CA creation, issuance, renewal, rotation, co-signing, revocation, deletion, CRL generation, PKCS#12 export) can be appended to an AuditLog. The log is a JSON-Lines file in which

  • every entry carries a sequence number, a UTC timestamp, the actor, the event name and its data;

  • every entry includes the SHA-256 hash of the previous entry (prev) and its own hash (hash), forming a hash chain — editing, inserting, reordering or deleting an entry in the middle breaks the chain;

  • every entry can be signed (sig) with a dedicated audit key or any CASigner (e.g. an HSM), so the chain cannot be silently recomputed by someone who can write the file but does not hold the key.

Truncation of the tail can only be detected against a head hash stored elsewhere: periodically publish AuditLog.head (ticketing system, SIEM, a second host) and pass it to AuditLog.verify() as expected_head.

Writes are serialised with a thread lock and, on POSIX, an exclusive flock so that several processes on one host can share a log file. flock is advisory and unreliable on network file systems; on Windows there is no inter-process lock — use one writer process there.

An entry is written only after the audited operation has completed, so a failure to write it (AuditLogError) means the operation took effect but is not recorded: treat it as an incident, do not simply retry. A crash in the middle of a write leaves an unterminated last line; the next AuditLog.record() cuts it off and records an audit.torn_entry_removed event with its size and SHA-256.
